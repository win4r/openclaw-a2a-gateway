**Conclusion:** This is a **dependency swap + adapter rewrite**, not a hand-coded port. The v1.0 SDK already implements the entire server-side wire format, the v0.3→v1.0 detection for outbound, and an optional legacy compat shim. We don't write the JSON-RPC method routing by hand; we use `jsonRpcHandler()` from the SDK.

### 2.3 `index.ts` (lines 322-324, ~493-625)
The fork currently has its own Express route wiring (`app.use("/a2a/jsonrpc", ...)`, `app.use("/a2a/rest", ...)`, `app.use(cardPath, cardEndpointHandler)`, plus hand-rolled JSON-RPC method dispatch in `src/jsonrpc-handler.ts` if it exists). v1.0 SDK replaces all three with one call each.

```diff
-  description: "OpenClaw plugin that serves A2A v0.3.0 endpoints",
+  description: "OpenClaw plugin that serves A2A v1.0 endpoints (v0.3 legacyCompat opt-in)",
```
And in the `register()` body, where the routes are mounted:
```diff
-    app.use(cardPath, cardEndpointHandler);
-    app.use("/.well-known/agent.json", cardEndpointHandler);
+    app.use("/.well-known/agent-card.json", agentCardHandler({ agentCardProvider: () => agentCard }));
+    app.use("/.well-known/agent.json",       agentCardHandler({ agentCardProvider: () => agentCard })); // legacy alias
     ...
-    app.use("/a2a/jsonrpc", createHttpMetricsMiddleware("jsonrpc"), jsonRpcRequestHandler);
+    app.use("/a2a/jsonrpc", createHttpMetricsMiddleware("jsonrpc"), jsonRpcHandler({
+      requestHandler: a2aRequestHandler,
+      userBuilder: bearerUserBuilder,
+      legacyCompat: { enabled: true },   // accept v0.3 message/send for transition window
+    }));
     ...
-    app.use("/a2a/rest", restRequestHandler);
+    app.use("/a2a/rest", restHandler({
+      requestHandler: a2aRequestHandler,
+      userBuilder: bearerUserBuilder,
+      legacyCompat: { enabled: true },
+    }));
```
The fork's existing `src/jsonrpc-handler.ts` (and any REST/REST handler module) becomes dead code after this swap and should be deleted in the same PR.

### 2.4 `src/client.ts` (line 13, 244, 399, 426)
```diff
-import type { MessageSendParams, Message } from "@a2a-js/sdk";
+import type { SendMessageRequest, Message } from "@a2a-js/sdk";
```
And every `MessageSendParams` → `SendMessageRequest`. The shape is the same at the surface level (a `Message` plus `configuration`) but v1.0 requires the new wrapping.

### 2.5 Outbound transport selection (`src/client.ts` line 118-133)
Currently builds `ClientFactory` with `JsonRpcTransportFactory`, `RestTransportFactory`, `GrpcTransportFactory`. v1.0 SDK keeps all three but adds the `legacyCompat` opt-in. To keep the fork talking to both v1.0 peers (Phronesis) and v0.3 peers (any older peer still around during transition):
```diff
     options = ClientFactoryOptions.createFrom(ClientFactoryOptions.default, {
       cardResolver: new DefaultAgentCardResolver({ fetchImpl: authFetch }),
       transports: [
-        new JsonRpcTransportFactory({ fetchImpl: authFetch }),
-        new RestTransportFactory({ fetchImpl: authFetch }),
-        new GrpcTransportFactory(),
+        new JsonRpcTransportFactory({ fetchImpl: authFetch, legacyCompat: { enabled: true } }),
+        new RestTransportFactory({ fetchImpl: authFetch, legacyCompat: { enabled: true } }),
+        new GrpcTransportFactory({ legacyCompat: { enabled: true } }),
       ],
     });
```
`legacyCompat` causes the factory to inspect `AgentInterface.protocolVersion` on the discovered card and pick the right transport implementation (v1.0 for ≥1.0, v0.3 for 0.3.x). Without it, v0.3 peers get "Method not found" — which is exactly the symptom we hit.

## 3. Risks and unknowns

| Risk | Mitigation |
|------|------------|
| The v1.0 SDK's `jsonRpcHandler` doesn't accept our existing `userBuilder` shape (we have a custom `bearer` middleware) | Confirmed at SDK `dist/server/express/index.d.cts`: takes `userBuilder: UserBuilder`. We build a thin adapter from our existing `pushAuthMiddleware` to `UserBuilder` in the same PR. |
| The 486 v0.3 unit tests reference v0.3-only shapes (e.g. `additionalInterfaces` in fixtures) | Run the suite before any change → baseline pass. Run again after the swap → expect breakage in fixture-mismatch tests, fix or mark `.skip` with TODO. Phases 2/3. |
| Doxa has Doxa-only OpenClaw operator extensions (`operator.read`/`operator.write` per CHANGELOG line ~55) that ride on top of the JSON-RPC envelope | v1.0 SDK's `jsonRpcHandler` accepts a custom `requestHandler: A2ARequestHandler` — we wrap our existing operator-scope check inside that adapter. No extension gets dropped. |
| `grpcProxy` field in `agent-card.ts:28` referenced by v0.3 plugin config | v1.0 doesn't recognize `grpcProxy` config key (the SDK computes gRPC URL differently). Keep accepting the config field in our parser but mark it as legacy/no-op in this release. |
| The v1.0 SDK's `AgentInterface` uses `protocolBinding`/`protocolVersion` (v1.0 names) but Doxa's existing v0.3 plugin peers use `transport` (v0.3 name) | v1.0 SDK's `DefaultAgentCardResolver` parses both via the `legacyCompat` flag. With `legacyCompat: { enabled: true }` on the JSON-RPC handler, inbound v0.3 cards still resolve. Outbound is covered by the same flag on the transport factories. |
| README says "v0.3.0" everywhere; downstream users will be confused | Phase 3 includes a documentation pass: replace "v0.3.0" with "v1.0 (v0.3 legacy compat opt-in)" in the README, CHANGELOG, and plugin manifest. |

## 5. Out of scope (deferred)

Per the agreed MVP scope:

- DNS-SD / mDNS discovery — works at both versions, no port needed; leave alone
- Push notifications — `pushNotifications: false` today, no behavior to break
- `tasks/cancel` method rename — v0.3 → v1.0 also renames this; `legacyCompat` covers it
- `SendStreamingMessage` → `StreamMessage` — fork supports streaming but Phronesis (Hermes) doesn't currently use it; v1.0 SDK handles both via `legacyCompat`
- gRPC transport parity — same SDK class, same config key, no work
- New `provider` field semantics (organization/URL) — added in v1.0 spec, but no spec-level contract for what it means yet; we set it to a static value
- Extended agent card support (`capabilities.extendedAgentCard: true`) — out of scope; flag stays `false`
